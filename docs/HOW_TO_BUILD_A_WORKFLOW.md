# Building and Using a Custom Workflow — Practical Guide

## Summary

You don't need to understand Restate internals to write a workflow. You need
to know: how to scaffold one, what few pieces you must fill in, and how to
start/monitor it through the CLI, REST API, and Kafka. This is that guide.

## Is everything under `workflows/` an example?

Yes. `workflows/content-enrichment` and `workflows/content-authoring` are both
reference implementations, not business logic you build on. `CLAUDE.md` names
`content-authoring` as the canonical reference (walked through decision by
decision in `docs/example-workflow.md`) and `content-enrichment` as the
minimal version of the same skeleton. `tests/fixtures/versioned-sleeper` is a
third one, but it's test-only — ignore it.

When you build a real workflow, it becomes its own new folder under
`workflows/`, sitting alongside these two examples, generated by the CLI (next
section) — never by copy-pasting an example by hand.

## 1. Scaffold a new workflow

```sh
pnpm pipeline new workflow order-fulfilment                    # REST only
pnpm pipeline new workflow order-fulfilment --kafka orders.placed   # + a Kafka trigger
```

This one command generates a full working skeleton in `workflows/order-fulfilment/`:
`package.json`, both `tsconfig`s, lint config, `metadata.json`, and the source
files below. It builds, lints, typechecks and deploys **as-is** — nothing is
half-wired. Do not hand-write these files; a dozen of them have to agree with
each other, and a mismatch only shows up as a deploy-time error.

| File it generates | What's already correct in it | What you actually write |
|---|---|---|
| `metadata.json` | kind, name, Restate name, version `0.1.0`, REST trigger, Kafka trigger if requested | `description`; later, real `config` values |
| `src/schemas.ts` | zod boilerplate structure | The real `Input`, `Output`, `Config` fields (replace the `id: z.string()` placeholders) |
| `src/api.ts` | The Restate binding, wired to your schemas | Usually nothing — only touch this if you rename the handler |
| `src/workflow.ts` | The `run` handler skeleton, with `ctx.set('trigger', …)` / `ctx.set('version', …)` already in place | The actual orchestration logic |
| `src/adapters.ts` (Kafka only) | An adapter function stub | The real mapping from your Kafka event shape to your workflow's input, and your skip/fail rules |
| `src/trigger.ts` (Kafka only) | Fully wired — don't touch | — |
| `src/unit.ts`, `src/contract.ts`, `src/main.ts` | Fully wired — don't touch | — |

After scaffolding, the CLI itself tells you the next steps:

```
Next: pnpm install
      write the handler in workflows/order-fulfilment/src/workflow.ts
      pnpm pipeline deploy order-fulfilment
```

If you used `--kafka`, it also reminds you to add that topic to `kafka-init`
in `compose.yaml` (Kafka topic auto-creation is off; an undeclared topic just
never receives anything).

## 2. `metadata.json` — what it is, what you edit, where it's stored

`metadata.json` is generated by `pnpm pipeline new`, already valid. You never
hand-write one from scratch. After scaffolding, you only touch a few fields
in it:

| Field | Who sets it | When you touch it |
|---|---|---|
| `apiVersion`, `kind`, `name`, `restateName` | Scaffold | Never — these are identity; changing `restateName` after deploying breaks the link to existing runs |
| `version` | Scaffold sets `0.1.0` | Bump it **every time you redeploy changed code** — any code change (including a reformat) needs a new version, or deploy fails with `VERSION_ARTIFACT_CONFLICT` |
| `description` | Scaffold sets a `TODO:` placeholder | Replace with a real one-line description |
| `visibility` | Scaffold sets `public` (workflow) / `private` (service) | Rarely touched — `private` means only other units can call it, not the public API |
| `config` | Scaffold sets `{}` | Add the real settings your handler reads (e.g. `{ "summaryMaxWords": 120 }`), matching your contract's `Config` zod schema |
| `triggers` | Scaffold fills in based on `--kafka` | Add more triggers here if needed, following the same shape |
| `dependencies` | Scaffold leaves empty | Add `{ "kind": "service", "name": "..." }` for every service/workflow you call |

Example, filled in:

```json
{
  "apiVersion": "ai-pipeline/v1alpha1",
  "kind": "workflow",
  "name": "order-fulfilment",
  "restateName": "OrderFulfilment",
  "version": "0.1.0",
  "description": "Prices and confirms an order",
  "config": { "currency": "INR" },
  "triggers": [{ "id": "api", "type": "rest" }],
  "dependencies": [{ "kind": "service", "name": "pricing" }]
}
```

### Where it's actually stored

Two places, and they can drift:

1. **On disk, in the repo.** `workflows/<name>/metadata.json` is a plain
   file, checked into git next to the code. This is the source of truth for
   what you intend to deploy.
2. **In Postgres — the catalogue — once you deploy.** `pnpm pipeline deploy
   <name>` reads this file, ships it to `core-api` (`POST /v1/deployments`),
   which writes it into the catalogue tables (`infra/postgres/init/20-catalogue.sql`).
   `GET /v1/workflows/:name` reads that row back — schemas, config, triggers,
   dependencies, versions, deployments.

If you edit `metadata.json` and don't redeploy, the file and the catalogue
disagree — the running system still reflects whatever was last deployed, not
your edit. The `version` field is exactly the mechanism that keeps this from
being ambiguous: a given version always means one specific, already-deployed
build.

## 3. What you actually need to know to write the handler

You do not need to understand how Restate persists its journal, how the
control plane reconciles subscriptions, or how the catalogue tables work.
You need these five things:

1. **Define your data shapes in `src/schemas.ts`.** Three zod objects:
   `Input` (what a caller sends), `Output` (what you return), `Config`
   (values read from `metadata.json`). Use `z.strictObject` — rejects
   unexpected fields.
2. **All I/O goes inside `ctx.run(name, fn, retryProfile)`.** Anything that
   calls an LLM, another service, a database, or an external HTTP API must be
   wrapped this way. `retryProfile` comes from `@ai-pipeline/runtime/retry`
   (`retry.llm`, `retry.http`, `retry.db` — pick the closest match, or write
   your own options object).
3. **Everything else must be deterministic.** No `Date.now()`,
   `Math.random()`, `new Date()`, or timers outside `ctx.run` — use
   `ctx.date.now()`, `ctx.rand`, `ctx.sleep()`. No native
   `Promise.all`/`race`/`allSettled`/`any` over durable work — use
   `RestatePromise.all([...])` instead. This is not a style guideline — lint
   fails the build if you break it.
4. **Call another service with `ctx.client(otherServiceApi).method(args)`,
   not a raw HTTP request.** This is what makes the call durable.
5. **Throw `restate.TerminalError(message)` for anything retrying won't
   fix** — bad input, a business rule violation, a model that flatly refused
   the request. Anything else you throw is treated as transient and retried
   according to the unit's retry policy (10 attempts, then the invocation
   *pauses* rather than fails — see section 6).

Two lines the scaffold already puts at the top of `run` — leave them in,
don't remove:

```ts
ctx.set('trigger', trigger);
ctx.set('version', metadata.version);
```

The runs API (`GET /v1/runs/:workflow/:runId`) reads these back to report how
a run started and which code version handled it.

### Minimal real example (adapted from `content-enrichment`)

```ts
export const orderFulfilment = restate.implement(orderFulfilmentApi, {
  handlers: {
    run: async (ctx, { input, trigger }) => {
      ctx.set('trigger', trigger);
      ctx.set('version', metadata.version);

      const { total } = await ctx.client(pricingApi).price({ items: input.items });

      return { orderId: input.orderId, total };
    },
  },
  options: workflowOptions(metadata),
});
```

### Calling multiple services at once

If two calls don't depend on each other, run them concurrently with
`RestatePromise.all` — never plain `Promise.all`:

```ts
const [a, b] = await RestatePromise.all([
  ctx.client(serviceAApi).method(x),
  ctx.client(serviceBApi).method(y),
]);
```

`content-authoring` does exactly this for two of its three service calls, then
makes the third sequentially because it needs the first two's results —
that's the pattern to copy for anything beyond a single dependent call.

### If your workflow depends on a service that doesn't exist yet

Scaffold the service the same way:

```sh
pnpm pipeline new service pricing
```

Then write its `handle` function the same rules apply to (all I/O in
`ctx.run`, `TerminalError` for permanent failures). Declare the dependency in
your workflow's `metadata.json`:

```json
"dependencies": [{ "kind": "service", "name": "pricing" }]
```

If a second unit will ever call that service too, move its schemas out of
`services/pricing/src/schemas.ts` into a new `packages/contract-pricing`
package (only when a second caller actually exists — not preemptively).

## 4. Deploying and iterating

```sh
pnpm install                       # after any scaffold or dependency change
pnpm pipeline deploy order-fulfilment [dependency-name ...]   # dependencies first
```

What `deploy` actually does, in order: builds the unit if its source changed
(skipped otherwise), starts a container for it, then registers that
deployment with `core-api`, which registers it with Restate and updates the
catalogue.

Two modes:

| Mode | Command | Behavior |
|---|---|---|
| Immutable (default) | `pnpm pipeline deploy order-fulfilment` | New container + new Restate deployment per build. Old deployment keeps serving in-flight runs, then drains. Any code change (even a reformat) requires bumping `version` in `metadata.json`, or you get `VERSION_ARTIFACT_CONFLICT` |
| Dev | `pnpm pipeline deploy order-fulfilment --dev` | Overwrites one `<name>-dev` container/endpoint in place. For local iteration only — not for anything you'd point real traffic at |

```sh
pnpm pipeline deployments order-fulfilment   # see what's deployed, in-flight counts
pnpm pipeline retire <deploymentId>          # once drained; refused otherwise
```

## 5. Using the CLI end to end

```
pnpm pipeline new <workflow|service> <name> [--kafka <topic>]
pnpm pipeline deploy <name...> [--dev]
pnpm pipeline deployments [name]
pnpm pipeline retire <deploymentId>
pnpm pipeline workflows                         # list the catalogue
pnpm pipeline start <workflow> --input '{...}' [--key <idempotency-key>]
pnpm pipeline runs [workflow] [--status s] [--limit n] [--cursor c]
pnpm pipeline run <workflow> <runId>            # show one run
pnpm pipeline cancel <workflow> <runId>
```

Example session:

```sh
pnpm pipeline start order-fulfilment --input '{"orderId":"o-1","items":["sku-1"]}'
# → { "runId": "...", "invocationId": "...", "status": "running" }
pnpm pipeline run order-fulfilment <runId>
# → shows status, and output once completed
pnpm pipeline runs order-fulfilment --status running
```

Config: `CORE_API_URL` (default `http://127.0.0.1:3000`) and `DOCKER_NETWORK`
(default `ai-pipeline`), read from `.env`.

## 6. Using the REST API directly

Base URL: `http://127.0.0.1:3000/v1` (core-api's HTTP port).

| What | Request |
|---|---|
| List catalogue | `GET /v1/workflows?kind=workflow` |
| Describe one workflow | `GET /v1/workflows/:name` — schemas, config, trigger state, dependencies, versions |
| **Start a run** | `POST /v1/workflows/:name/runs` with body `{ "input": {...} }`, optional header `Idempotency-Key: <key>` → `202 { runId, invocationId, status }` |
| Toggle a trigger | `PATCH /v1/workflows/:name/triggers/:id` with `{ "enabled": true|false }` |
| List runs | `GET /v1/runs?workflow=&status=&limit=&cursor=` (paginated, default 50) |
| Read one run | `GET /v1/runs/:workflow/:runId` — includes `output` once completed |
| Cancel a run | `POST /v1/runs/:workflow/:runId/cancel` — graceful, handler unwinds |
| Kill a run | `POST /v1/runs/:workflow/:runId/kill` — immediate, no unwinding, children abandoned |
| Resume a run | `POST /v1/runs/:workflow/:runId/resume` — revives a `paused` run |
| Register a deployment | `POST /v1/deployments` (used by the CLI, not usually called by hand) |
| List deployments | `GET /v1/deployments?name=` |
| Retire a deployment | `DELETE /v1/deployments/:id` — refused until drained |
| Health | `GET /health/live`, `GET /health/ready` |

```sh
curl -s localhost:3000/v1/workflows/order-fulfilment/runs \
  -H 'content-type: application/json' \
  -H 'idempotency-key: demo-1' \
  -d '{"input":{"orderId":"o-1","items":["sku-1"]}}'

curl -s "localhost:3000/v1/runs/order-fulfilment/<runId>"
```

Run statuses: `running`, `completed`, `failed`, `cancelled`, `paused`.
`paused` is a designed state, not a bug: the `llm` retry profile (and any
uncapped profile) never fails a run on exhaustion — it pauses the *invocation*
instead, so a gateway outage doesn't destroy the run's progress. Find paused
runs with `GET /v1/runs?status=paused`, fix the underlying cause, then
`POST .../resume`.

Errors always come back as `{ "error": { "code", "message" } }`; the codes are
a shared union in `@ai-pipeline/api-contract/errors`.

## 7. Using a Kafka trigger

A Kafka trigger is declared once in `metadata.json`:

```json
"triggers": [
  { "id": "api", "type": "rest" },
  {
    "id": "orders-placed",
    "type": "kafka",
    "cluster": "local",
    "topic": "orders.placed",
    "adapter": "ordersPlacedEvent"
  }
]
```

- `cluster` is the Kafka cluster name as registered with Restate.
- `topic` is the raw Kafka topic name.
- `adapter` names an exported function in `src/adapters.ts`.

The adapter is a **pure function**: `(event: unknown) => Input | null`.

```ts
export const adapters = {
  ordersPlacedEvent(event: unknown): OrderFulfilmentInput | null {
    const parsed = OrdersPlacedEvent.parse(event);
    if (parsed.status !== 'confirmed') return null;   // not our business: skip silently
    return { orderId: parsed.id, items: parsed.items };
  },
};
```

The contract is deliberate and important:

| Adapter behavior | What happens |
|---|---|
| Returns a valid object | A run starts |
| Returns `null` | The record is dropped silently — no run, no error, nothing logged as a failure |
| Throws | The record fails **terminally** — it is never retried and never blocks the rest of the partition |

`content-authoring`'s adapter is the real-world pattern to copy: it returns
`null` for object types this workflow doesn't care about (a `Collection` or a
`Draft`), but throws when a `Live` content item is missing text it actually
needs — that distinction (skip vs. fail) has to be a deliberate choice you
make per field, not a default.

Two things to remember operationally:

- **The topic must exist before you can subscribe to it.** Auto-creation is
  off; add your topic to the `kafka-init` job in `compose.yaml`.
- **A run id is derived from the Kafka record's own coordinates**
  (partition + offset, and cluster/topic/trigger id), not generated randomly
  — so the same physical message reliably maps to the same run even if Restate
  redelivers it.

Publish a test event by hand:

```sh
echo '{"id":"o-1","status":"confirmed","items":["sku-1"]}' | \
  docker compose exec -T kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic orders.placed
pnpm pipeline runs order-fulfilment
```

If a subscribed topic disappears and comes back (e.g. Kafka recreated without
its volume), Restate's consumer for it stops — recreate the subscription by
toggling the trigger off then on:

```sh
curl -X PATCH localhost:3000/v1/workflows/order-fulfilment/triggers/orders-placed \
  -H 'content-type: application/json' -d '{"enabled":false}'
curl -X PATCH localhost:3000/v1/workflows/order-fulfilment/triggers/orders-placed \
  -H 'content-type: application/json' -d '{"enabled":true}'
```
It resumes from its last committed offsets.

## 8. Testing what you wrote

| Test type | File pattern | What to check |
|---|---|---|
| Unit tests | `src/*.test.ts` | Adapters (the skip/fail rule), pure step functions, schema edge cases |
| Replay test | `src/*.replay.test.ts` | Runs your handler against a real (Testcontainers) Restate instance and proves the result is identical across a journal replay — **required for any handler logic change** (`pnpm test:replay`) |
| E2E | `tests/e2e/*.test.ts` | Full stack: both triggers, versioning, crash recovery |

`pnpm check` is the overall gate: build, typecheck, lint (including the
determinism rules), unit tests, formatting, then `turbo boundaries` (checks
the package dependency graph is legal).
